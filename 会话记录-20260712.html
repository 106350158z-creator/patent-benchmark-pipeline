抓取方法是怎么改过来的

最开始想省事，直接借鉴 markush 文件夹下已有的抓取代码。但真跑起来发现根本套不上，原因不是代码写得不好，而是目标网站完全不是一回事。

为什么借鉴 markush 的方法没奏效

翻了一遍 markush 仓库，它其实压根没有抓 EPO 的代码。它只覆盖两个数据源，两条路都解决不了 EPO 这边的问题：

markush 的方案针对的站搬到 EPO 为什么不行
裸 HTTP 请求（urllib）+ 免费代理池轮换USPTO data.uspto.govUSPTO 前面只是普通 WAF；EPO Register 前面是 Cloudflare 的机器人管理 + Turnstile 人机验证，还会校验 TLS 指纹。免费代理既不能跑 JS，也拿不到合法的 cf_clearance，直接被挡。
Playwright 登录后在页面里 fetch 拿 APICNIPA（中国）cpquery.cnipa.gov.cnCNIPA 是登录换 token、动态参数塞进请求；EPO Register 不需要登录，卡点在过 Cloudflare 那一关，登录那套逻辑用不上。

再加上 markush 那边失败了就立刻换代理、没有重试和退避，请求头也只有一个固定 UA，缺 Cloudflare 会查的那些字段。所以结论很直接：markush 没有"过 Cloudflare 的工具"，无论借哪一段都解不了 EPO 这层墙。

后来是怎么一步步改的

认清 Cloudflare 是真正的关卡之后，思路从"想办法伪装请求"换成"干脆用一个真的、已经过了验证的浏览器去抓"。中间迭代了几版：

  • 第一版：Playwright 自己开浏览器（download_epo_docs_browser.py）。用持久化用户目录、关掉自动化特征，靠 page.goto 拿 PDF，遇到 challenge 就等着重试。问题是每次新起的浏览器还是容易被 Cloudflare 认出来，过验证不稳定。
  • 第二版：改成 CDP 附着（download_epo_docs_cdp.py）。不再让脚本自己开浏览器，而是手动开一个真 Chrome、人工过一次 Cloudflare，脚本通过调试端口（9222）连上这个已经"干净"的浏览器，在页面里用 fetch(url, credentials:'include') 借它的 cookie 把 PDF 取出来、转 base64 传回 Python。这一版终于能稳定拿到文件。
  • 第三版：做成批量 + 抗卡死 + 失败分级（collect_epo_docs_cdp_batch.py，也就是现在这个）。在第二版基础上加了后台线程硬超时、429/403 分级处理、节点轮换、断点续跑——这些就是下一节"过程里解决的几个问题"讲的内容。
一句话：markush 的方法解决的是"没有反爬或只有普通 WAF"的站；EPO Register 是 Cloudflare 站，必须借一个真人过了验证的浏览器，这条路是重新趟出来的，不是抄来的。

关于"抓一半失败"

本周有文件落盘的 1,044 个 case，最终状态是这样的：

状态数量说明
ok 完成486完整跑完
error 半成品120抓到几个文件后中途被挡，最终标失败
无状态记录438跨批次 / 早期 run，状态表没覆盖到

关键的一点：标 error 且一个文件都没有的 case 数量是 0。凡是真的跑过的，哪怕最后失败，也至少抓到了几个 PDF，这部分文件都是能用的。所以"涉及 case 数大于完成数"，差额主要就是这 120 个半成品，加上跨批次没被状态表统计到的那批。

过程里解决的几个问题

1. 抓着抓着卡死

批次遇到一个特别大的 PDF（base64 后接近 48MB）时，整条 CDP 通道被顶住，卡了差不多 9 分钟没动静。原来的超时机制拦不住这种传输层的堵。

改法：让一个专门的后台线程持有所有 Playwright 对象，主线程通过队列下命令、用带硬超时的 queue.get(timeout) 等结果。一旦超时就直接弃用那个 worker 重建，Chrome 本身不退出，不用重新过验证。

2. 失败策略重做

老逻辑碰到 403 会死磕重试 45 秒，还得整个 case 跑完才轮换节点，很拖。重新分了三类来处理：

情况处理
429 限流原地指数退避，重试同一节点，不刷新不轮换
403 / 请求被中止快速止损，先轻量刷新会话；连续挡几次才轮换节点；然后把 case 重新排队
CDP 硬超时弃用 worker 重建会话

3. 断点续跑

--skip-existing 扫 801 条记录只要 0.12 秒，重启不会重下已有文件。

真正的瓶颈

不是节点坏，也不是文件不存在，而是单 IP、单浏览器会话下 EPO 加 Cloudflare 的按 IP 限流。

日志里 block 的原因，429 限流占了一半以上。三轮调参都卡在每个 case 大约 7 分钟这个天花板上下，动不了。好在整个过程 err 计数保持为 0，没丢文件。另外，轮换节点太激进会烧掉 cf_clearance，触发那个需要手动点的"请验证您是真人"。
