专利审查 Benchmark Pipeline 改进说明

这次改动的目标不是只把 HTML 做得更好看，而是让抓取、分析、证据、Claim 和最终展示都能被复核、能批量重跑、能说明为什么可靠。

一句话：从“生成一个 demo”升级为“可复用、可回查、可交给标注人员检查的流程”。
9 / 9 疾病分类样例完整性校验通过
14 本次涉及新增或修改的 pipeline 脚本
可回查 HTML 里的原文证据可以回到本地 OCR/TXT
总体思路 风险原文 证据回查 Claim 校对 批量刷新 质量门 输入稳定性 Markush/引用先文 脚本索引

总体思路

1. 展示层少总结，多原文

风险和建议不再默认展示模型写出来的英文总结，而是展示审查材料里的连续原文和中文翻译。

2. 法律文本单独校对

Claim 不再被默认视为 OCR 准确文本，而是生成草稿后人工对照 PDF 校对。

3. 每一步都能批量验证

增加完整性、证据匹配、质量审计和批量刷新脚本，减少手动操作导致的不稳定。

01

风险原因 / 建议依据改成“审查原文句子”

为什么做：原来的风险和建议更像模型摘要，给外部同学看时容易误解为 EPO 原文。现在展示层优先显示可回查的原始句子。

展示可信度提升
  • 新增 risk_source_sentences：风险依据原文列表。
  • 新增 action_basis_source_sentences：建议依据原文列表。
  • HTML 标题从“建议动作”改成“建议依据原文”，避免把模型建议包装成官方建议。
  • 老字段 top_risk_reasons 和 recommended_actions 仍保留，用于内部分析和旧文件兼容。
生成逻辑 HTML 渲染 EP16823054 HTML

例子：EP16823054 的“风险原因”来自授权决定 OCR

字段risk_source_sentences[0]
维度support
来源12-03-2021_Decision_to_grant_a_European_patent_E5YA3YJI3435DSU_ocr.txt
FollowingexaminationofEuropeanpatentapplicationNo.16823054.8aEuropeanpatentwiththetitle and thesupporting documentsindicated in thecommunicationpursuant toRule71(3) EPC(EPOForm 2015,A52) dated 19.11.20ishereby granted...

展示时同时给中文翻译：“经对欧洲专利申请号16823054.8进行审查，依据 Rule 71(3) 通知中所示文件，现授予欧洲专利。”

02

增加证据回查和自动修复

为什么做：模型可能生成“看起来像原文”的句子，但如果本地 OCR/TXT 找不到，就不能作为可交付证据。

减少幻觉证据
  • verify_report_sources.py 会扫描 JSON 中的 original_text，和本地文本做匹配。
  • repair_report_sources.py 会把匹配较弱的片段替换成本地文件里的连续摘录。
  • 旧的模型摘要字段不再作为“原文证据”检查对象，避免把总结句误判为原文。
  • 批量刷新流程里默认先修复，再校验，最后才生成 HTML。
python scripts/verify_report_sources.py \
  疾病分类9个样例/代谢性疾病/EP16823054/EP16823054-analysis.json \
  --case-dir 疾病分类9个样例/代谢性疾病/EP16823054 \
  --min-score 0.88

例子：EP16823054 证据命中情况

证据总数29
宽松归一化命中29 / 29
质量状态pass
来源疾病分类9个样例/_quality_audit.csv

这意味着 HTML 里展示的原文依据，不只是模型输出，而是可以在本地 OCR/TXT 里找回来的。

03

Claim 文本改成“PDF 权威来源 + 人工校对”工作流

为什么做：化学 Claim OCR 很容易出现空格、上下标、取代基、编号错误，不能当法律级准确文本。

法律文本风险隔离
  • 新增 EPxxxx-claims-verified.json，保存 Claim 编号、文本、页码、校对状态、来源 PDF SHA256。
  • 新增 EPxxxx-claims-review.html，左侧是 OCR 草稿，右侧是 PDF 页面图片，方便人工对照。
  • HTML 中未校对时显示 Claim OCR Preview 或 Claim Draft Preview。
  • 全部 Claim 标成 verified 后，HTML 才展示 Verified Claims。
Claim 校对脚本 EP16823054 Claim Review EP16823054 Claims JSON

例子：EP16823054 当前 Claim 状态

来源类型ocr_preview
校对状态needs_human_review
Claim 数0 / 26 verified
草稿来源19-08-2020_Claims_E453Q0P71436DSU_ocr.txt

这不是说不能展示 Claim，而是明确告诉使用者：当前是 OCR 预览，法律文本要以 PDF 和校对后的 JSON 为准。

04

把多步手工流程封装成批量刷新脚本

为什么做：以前每一步单独跑，参数、顺序、遗漏文件都会影响结果。现在可以对一个 case set 统一重跑。

复用性提升
  • run_case_set_refresh.py 串起 PDF 文本提取、OCR、Claim 草稿、benchmark input、Markush、analysis、证据修复、校验、HTML。
  • 每个案件完成后写入 _refresh_status.csv，方便定位失败案件。
  • 支持 --stage prepare / --stage analysis / --stage all，便于增量运行。
  • 关键参数集中在命令行，方便以后换模型、调 OCR、调证据阈值。
python scripts/run_case_set_refresh.py 疾病分类9个样例 \
  --stage all \
  --model gpt-5.5 \
  --verify-min-score 0.88

例子：这 9 个疾病样例可以一条命令刷新

代谢性疾病3 个 EP 案件
肿瘤3 个 EP 案件
自身免疫3 个 EP 案件
输出JSON + HTML + CSV

组会时可以强调：这不是为 9 个样例手写的临时代码，而是后续 case set 也能复用的批量处理入口。

05

增加完整性校验和质量审计

为什么做：HTML 能打开不代表结果可靠。必须检查原始文件、OCR、分析字段、证据链和案件结果是否齐全。

交付前质检
  • validate_case_set_completeness.py 检查 register、doclist、PDF、TXT/OCR、analysis JSON、HTML 必要区块。
  • audit_case_quality.py 输出每案 Claim 字符数、证据命中数、source 文档数、案件结果一致性。
  • 支持 --require-verified-claims，以后人工校对完 Claim 后可以打开法律级 Claim 校验。
  • 质量问题会进入 CSV，不需要逐个 HTML 人眼找缺失字段。
质量审计 CSV 完整性校验 CSV

例子：9 个样例完整性全部通过

EP16823054pass，docs 15，original 3
EP17191704pass，识别为 withdrawn，grant_label = no
EP18826609pass，docs 32，original 5
总体9 / 9 pass

这里能说明“文件齐全、字段齐全、案件状态没有明显错配”，适合作为给标注人员分发前的质量门。

06

改进分析输入稳定性

为什么做：如果模型拿到的 SOURCE 太少、只有 register HTML，或者路径解析错，输出就会漂。

降低随机波动
  • 改进路径解析：benchmark input 里的相对路径会按 case 目录解析，而不是依赖当前终端目录。
  • 默认把 SOURCE 控制在审查文本文件，不再默认把 register HTML 当主要分析证据。
  • 增加 source quality gate：Claim 太短、SOURCE 太少、文本量太低时直接报错。
  • split 分析模式增加重试：如果某个维度缺少 score 或 original_text，会重新要求模型输出完整 JSON。
单次分析脚本 分维度分析脚本

例子：EP16823054 的 SOURCE 质量

source docs8
TXT 文件23
OCR 文件8
source 字符量160,503 meaningful chars

这个改动的价值是：模型分析前先确认“它看到的材料是足够的审查文件”，而不是靠一次偶然输入跑出结果。

07

Markush 图片和引用先文增加可解释状态

为什么做：以前图片或引用先文为空，只能看到“空”。现在可以知道是没有公式上下文、页面没定位到，还是候选图被过滤掉。

方便排查空结果
  • render_markush_pages.py 新增 markush_extraction_status。
  • 状态里记录 snippets、page jobs、candidate images、selected images 的数量。
  • build_benchmark_input.py 增强引用先文抽取，优先从审查文本和 register documents cited 中找专利号。
  • HTML 会把 benchmark input 里的引用先文合并进证据链，不完全依赖 LLM 自己列举。
Markush 渲染脚本 引用先文抽取

例子：EP16823054 的图片和引用先文

Markush 状态selected
候选图48 candidates，自动选出 3 张
页面定位9 pages，8 snippets
引用先文WO2012019188、WO2009049165

这类状态可以直接告诉检查同学：有些案子没图，不一定是程序坏了，可能是没有找到 Formula/Markush 上下文或候选图没有通过结构图过滤。

脚本索引：组会上可以这样讲

脚本 这次改进点 对结果稳定性的作用
run_case_set_refresh.py 新增批量刷新入口，串联 OCR、Claim、分析、修复、校验、HTML。 减少手动跑漏步骤、参数不一致的问题。
generate_claims_verified.py 新增 Claim 草稿 JSON 和 review HTML。 把 OCR 预览和法律级 Claim 文本分开。
generate_analysis_json_split.py 新增原文依据派生、SOURCE 质量门、缺字段重试。 让模型输出更完整，降低证据字段为空的概率。
json_to_html_report.py HTML 优先展示原文依据、Verified Claims、Markush/引用先文。 让外部复核人员看到的是可解释、可追溯结果。
repair_report_sources.py 把弱匹配的原文证据替换成本地连续摘录。 减少模型改写句子进入 HTML。
verify_report_sources.py 校验所有 original_text 能否回查到本地文本。 给“证据可追溯”加硬性检查。
validate_case_set_completeness.py 检查原始 PDF、TXT/OCR、analysis 字段、HTML 区块。 交付前确认每案材料齐全。
audit_case_quality.py 输出质量审计 CSV，包括证据命中、Claim 状态、案件结果。 用表格快速定位需要人工复核的案件。

建议汇报话术

一段话版本

这次我主要把原来的 demo 流程做了工程化改造。以前 HTML 里有些字段更像模型总结，Claim 也主要依赖 OCR，所以结果不够稳定、也不方便交给别人复核。现在我把风险和建议改成展示审查文件原文，并加了本地证据回查；Claim 改成 PDF 权威来源加人工校对的流程；同时把 OCR、分析、证据修复、HTML 渲染、完整性校验串成批量脚本。这样 9 个样例不仅能生成结果，还能说明每个字段来自哪里、哪些内容已经校对、哪些内容还只是预览。

备注：本页中的例子来自仓库当前的 疾病分类9个样例 输出结果。Claim 相关示例显示为 needs_human_review 是预期状态，表示法律级文本仍需人工对照 PDF 校对。
